The KVIS Mini-HPC Cluster (BistKA) is a dedicated high-performance
computing environment designed to support advanced computational work at KVIS.
It provides CPU, GPU, and high-memory resources for data-intensive and
simulation-based workloads that exceed the capabilities of standard desktop
machines. The cluster exists specifically to enhance research project and learning in
computationally demanding classes, enabling students and project teams to run
real-world scientific, engineering, and data science workloads.

Policies

Policies

Policies
"

Any individual or group wishing to use the KVIS Mini-HPC Cluster (BistKA) must submit an
internal request by completing and uploading form (FM-HPC-01, FM-HPC-02, FM-HPC-03A or
FM-HPC-03B).
All users must strictly comply with all policies outlined below.

Purpose

#

The KVIS Mini-HPC Cluster (BistKA) may only be used for three purposes: (1) Student
Projects, (2) Teacher Projects, and (3) School Classes that require high-performance
computing workloads (CPU/GPU, high-memory)

Terminologies
1. Student Project : Academic research conducted by students that requires computational
resources to complete tasks.
2. Teacher Project : Academic research conducted by teachers that requires computational
resources to complete tasks.
3. School Class : A course o!ered under the KVIS curriculum that requires computational
resources for instructional purposes.
4. Project : Refers to both Student Projects and Teacher Projects.
5. Group : A general term that refers to a Student Project, a Teacher Project, or a School Class.
6. Job : A unit of work submitted to the HPC cluster for execution.
7. User Log-in Account : Personal account. Examples include: s00345, t651009.
8. SLURM Account : An account used to submit jobs and track computing credits. Examples include:
s00345, t651009, 25sfcs01, 25sebl01, 25t01, 25cma30102.
9. Partition : A category of compute resources that defines the maximum runtime and task priority

for submitted jobs.
10. Walltime : The maximum duration a job is allowed to run on a compute resource. Once this time
limit is reached, the job will be terminated automatically.
11. Feb 28 : Refers to February 28 in a common year, or February 29 in a leap year.
12. Credit : The amount of resource usage for jobs in SLURM.
13. SHr : A unit of credit, where 1 SHr is based on 1 hour of usage on 1 physical processor core.

Good Practices and Usage Guidelines
1. You can connect to the master node via CMD, Zsh, Terminal, or any other shell platform. We also
recommend using platforms of programs from Login & File Transfer . VS Code is not
recommended, BistKA blocks all vscode-server processes started by Remote - SSH extension,
as it consumes a large amount of system resources when working with the cluster.

2. Try not to run code directly on the master node (i.e., without submitting a job), as it consumes
the master node’s resources and may cause delays or lag in the command-line interface.
3. Request only the resources you actually need, such as CPU cores, RAM, and walltime.
4. Regularly delete unnecessary files to reduce storage usage.
5. Never share your user log-in account password with others.
6. Always log out after finishing your work.

Access & Usage Policy

"

Only eligible students (those with a Project ID or enrolled in a computational class) and
eligible teachers (who advise a student project, have informed the Deputy Director of
Academic A!airs, or teach a computational class) can register to use the KVIS Mini-HPC
Cluster (BistKA).
The access is granted via CLI using a username and password.

1. Only students with a school-assigned Project ID or those enrolled in a computational class, and
teachers who either advise a student project, have informed the Deputy Director of Academic
A!airs, or teach a computational class, are eligible to register for the use of the KVIS Mini-HPC
Cluster (BistKA).
2. The cluster is for high-performance computing workloads (CPU/GPU, large-memory).
3. All jobs must be directly related to an approved school project or coursework for a
computational class; personal or unrelated tasks are not permitted.
4. The requests for student project modification to use the mini-HPC cluster must be reviewed and
processed in accordance with the school’s procedures and regulations.
5. Project status must be re-verified every academic year on Feb 28.

Job Policy
Jobs are run on a first-come, first-served basis with possible backfilling for short jobs.

"

The master node is for login, file transfer, and code compilation only. All compute work
(including Jupyter and ipykernel) must run inside SLURM jobs, and any unauthorized or
excessive resource usage on the master node will be terminated automatically.

1. Jobs are scheduled on a first-come, first-served basis, subject to resource availability (CPU/GPU,
memory) and the requested wall time. Short jobs may be backfilled.
2. All submitted jobs must specify both the partition and SLURM account.
3. All jobs must be run from the CLI; graphical user interfaces are not supported on this system.
4. The master node may be used only for logging in to submit jobs, upload/download files, and compile
programs. Any process that exceeds the allowed CPU cores, memory (RAM), or runtime will be
terminated automatically.

Therefore, the Total credit (SHr) usage per job is calculated as:

SHr = Nnodes × [(αcpu Ncores ) + (αmem M em) + (α4500gpu Ngpus ) + (α4000gpu Ngpus )] × Texec
where
Texec : Execution time in hours,
Ncore : Number of CPU cores allocated per node,
M em : Memory size allocated per node, in GiB,

$

N4500gpu : Number of RTX PRO 4500 GPUs allocated per node,
N4000gpu : Number of RTX PRO 4000 GPUs allocated per node,
αcpu (= 1.0) : Weight per CPU processor core,
αmem (= 0.1) : Weight of memory size per GiB,
α4500gpu (= 7.0) : Weight per RTX PRO 4500 GPU accelerator,
α4000gpu (= 5.0) : Weight per RTX PRO 4000 GPU accelerator.

ModuleUtility

Module Utility

Module Utility
Introduction
On the BistKA , many applications are provided through a module system based on Lmod . In
Linux, your “working environment” is defined by a collection of environment variables—named
values that programs use to locate files, libraries, and configuration settings. Common examples
include $HOME , which points to your home directory, and $PATH , which lists directories where
the system looks for executable programs. While a default set of variables is created when you open
a shell, this environment often needs to be adjusted for scientific software (for example, setting
license variables or adding specialized compiler and MPI paths).
The module utility (commands $ module or $ ml ) provides a clean way to manage this
environment on BistKA . Each installed software package (and often each version) is described by
a modulefile that knows which environment variables to set or modify: paths to executables and
libraries, required dependencies, and any additional configuration. By loading a module for a
particular application, all relevant variables are automatically configured for you; by unloading it,
those changes are cleanly removed. This allows users to switch between di!erent software stacks
and versions without manually editing their environment, ensuring that jobs run with the correct
compilers, libraries, and tools on the BistKA system.

Job Scheduler

Job Scheduler
On the BistKA , users do not run heavy applications directly on the login (master) node. Instead,
all workloads are sent as jobs to the SLURM scheduler, which assigns them to suitable compute
nodes. Each job specifies both the actual task to perform (the program to execute, required input
files, and output locations) and the resources it needs, such as number of CPU cores, memory size,
GPU type and quantity, time limit, and target partition.
Jobs on BistKA are executed as batch jobs, meaning they run in the background without the user

needing to stay logged in. A typical workflow is: the user logs in to the BistKA master node,
prepares a SLURM job script (or uses $ srun / $ sbatch commands) that specifies the
application and resource requests, then submits the job to the scheduler. SLURM places the job in a
queue, matches it with available resources according to the cluster policies and priorities, and starts
it on one or more compute nodes. The user can safely log out while the job is running and later log in
again to check status and retrieve results.

▸ The job is given the name “test123” and

The script begins with #!/bin/bash , known as the shebang. This tells the system to interpret the
submission script using the Bash shell, so the file is both a SLURM job script and a standard Bash
script.
Next, the script contains several lines starting with #. In a Bash script these lines are comments and
are ignored by the shell. However, any line that starts with #SBATCH is treated by SLURM as a
directive that requests specific scheduling resources. It is crucial that all #SBATCH lines appear
before any executable commands in the script; if a #SBATCH directive appears after a Bash
command, SLURM will ignore it.

The directive #SBATCH --nodes=n specifies how many compute nodes the scheduler should
allocate for the job. In the example, only one node is requested. Be careful with single-process, multithreaded applications (such as MATLAB): they cannot run across multiple nodes, so requesting more
than one node (e.g. #SBATCH --nodes=2 ) will usually result in one node doing all the work
while the others remain idle.
The maximum runtime (walltime) is set using #SBATCH --time=T , where T is in the format
hours:minutes:seconds (e.g. 01:00:00 for one hour). The job should normally complete within
this limit. Once the specified time is reached, SLURM will terminate the job even if it is still running.
You can also assign a human-readable name to the job with #SBATCH --job-name="name" ,

SLURM Job Submission
After you have prepared a submission script (for example, script.sh # ), you send the job to the
scheduler with:
1

$ sbatch script.sh

SLURM will immediately print a numeric JobID and return you to the Linux prompt. At this stage,
the job has been accepted by the system and placed in the queue.
The job will usually remain in the PENDING state until the required resources become available.
How long it waits depends on several factors, such as overall cluster load, your requested
CPUs/GPUs/memory, and any partition or time-limit constraints.
When the job actually starts running, Slurm creates one or more output files named like slurm-

<JobID>.out (for example, slurm-1234.out ). By default, these files are written to the
directory where you ran sbatch, unless your script explicitly changes to another directory.

SLURM Interactive Job Submission
On the BistKA , interactive jobs are used when you need a live shell on a compute node instead of
running heavy commands on the master node. Typical use cases include testing and debugging
code, exploring data, trying modules, or quickly checking that a program runs correctly before you
turn it into a proper batch job. Instead of typing $ srun directly each time, you should start an
interactive session via the helper script $ sinteractive , which automatically sets up a suitable

$ srun --pty ... command, chooses a partition (e.g. compute-devel by default), and

asks for an account if needed. Once the job starts, you are “inside” a Slurm job on a compute node,
but you interact with it just like a normal Linux shell.
In practice, you log in to BistKA , then launch an interactive job with $ sinteractive and let
Slurm allocate resources (CPUs, memory, and optionally GPUs) for you. While you are in that
interactive shell, you can load modules, run compilers or Python, and test your code without
overloading the login node. When you finish, typing $ exit closes the shell and immediately frees
the resources for other users. Interactive jobs should be short and lightweight; longer production
runs should be submitted with $ sbatch instead.

CondaPip

Conda and Pip via Miniforge3

Conda and Pip via Miniforge3
pip is Python’s standard package installer—it pulls libraries from the Python Package Index (PyPI)
and installs them into your current interpreter or virtual environment. conda is a cross-platform

environment and package manager that creates isolated environments and installs prebuilt binaries
for both Python and non-Python dependencies (e.g., CUDA, MKL), which is especially helpful on HPC
systems.
A common workflow is: create a fresh conda environment, install as much as possible from the
conda-forge channel, then use pip inside that activated environment for anything not available on

conda . This keeps dependencies reproducible and avoids conflicts; avoid installing into base or
using pip --user. On BistKA , load Miniforge3/25.3.0-3 to get conda/mamba and use
them within a SLURM job.

How they di!er
▸ Scope: pip handles Python packages; conda handles Python and non-Python deps
(compilers, MKL, CUDA libs, etc.).
▸ Binaries: pip installs wheels/source from PyPI; conda installs curated binary builds from
channels.
▸ Environments: pip relies on venv/virtualenv; conda creates and manages its own envs.
▸ Dependency solving: conda solves the whole stack (often fewer compiler headaches). pip
resolves Python deps only.

When to use which
▸ Try $ conda first for scientific/ML stacks (NumPy/SciPy/PyTorch/CUDA), or when you need
native libraries.
▸ Use $ pip for packages that aren’t on conda, or to add a few extras inside an already-activated
conda env.
▸ It’s common to mix: install the heavy stack with $ conda , then $ pip install the
missing Python-only libs.
